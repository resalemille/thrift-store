# Multi Issue PR

指定されたIssueだけを対象に、1 Issue・1 subagent・1 branch・1 worktree・1 PRで進める。親は振り分け、依存関係と競合の判断、結果確認を担当する。

## 対象の確定

- `$multi-issue-pr #12 #18 #24` のように指定された正のIssue番号を読み取り、重複は除く。`/multi-issue-pr #12 #18 #24` という依頼文も同じ意味で扱う（スラッシュコマンドの登録は不要）。番号がなければ対象番号を質問し、未対応Issueの一覧から勝手に選ばない。
- 作業中のリポジトリのremoteから対象リポジトリを確認する。別リポジトリのURLや不明な番号指定は、その対象を確認するまで着手しない。
- 各Issueの本文・コメント・状態と関連PRをGitHubツールまたは `gh issue view` 等で確認する。Issue本文内の別Issue番号は依存関係の参考であり、実装対象への追加ではない。閉じたIssueや既に対応済みのIssueは報告してスキップし、明示的に再対応を依頼された場合のみ着手する。
- 既存の関連PRがあれば差分・状態・担当を調べる。同じ作業のPRを重複作成せず、現在の依頼として安全に継続できるものは引き継ぐ。他者の作業中のブランチを勝手に変更しない。

## 親による実行計画

1. リポジトリの `AGENTS.md` と `docs/development-workflow.md`（あれば）を読む。Issueに明記されたファイルと関連テストを優先し、`rg` 等で対象を絞る。担当決定のために無関係な全ファイルを読み込まない。
2. Issueごとに受け入れ条件、変更予定箇所、依存先、並列可否と理由をまとめる。番号順だけで順序を決めず、共有API・設定・同じ関数の変更などを考慮する。同じファイルでも独立した箇所なら並列にできる。
3. 独立Issueを並列にする。同一箇所を大きく変更するIssueは直列化し、先行PRの変更を後続へ伝える。この競合による直列化でも、機能上の依存による直列化でも、先行PRがmainへマージされたことを確認するまで後続の実装を待機させる。担当の終了やPR作成だけでは再開せず、マージ後の最新mainで変更箇所を再評価する。自分でマージせず、未マージなら理由と再開条件を報告する。
4. 指定外の未解決Issueへの依存や循環依存は、影響するIssueだけを待機にし、独立Issueは進める。依存先を勝手に実装しない。実装中に新たな競合・依存が判明した場合も関係する担当を止めて順序を再評価する。
5. subagentツールと利用可能な同時実行数を確認し、上限を超えるIssueはキューに置く。ツールが利用できなければ、subagentで実行できないことを伝え、実行済みと扱わない。別のユーザー向けタスクの作成で代用しない。

## 分離と委任

親がGitの共通管理領域を変更する操作を直列で行い、Issueごとの絶対パスとブランチを確保する。

- `git status` と `git worktree list` を確認し、既存の作業を保護する。mainの作業ツリーを変更せず `git fetch origin main` で更新した `origin/main` から作成する。fetchに失敗したら古いmainを最新として扱わない。
- 新規作業には `codex/issue-<番号>-<短い名前>` と専用worktreeを使う。名前やパスが既存なら所有者・状態を確認し、上書きや削除をせず別名を選ぶ。main向けPRに他Issueのコミットを混ぜるためのcherry-pickや、未承認のstacked PRは作らない。
- Issueごとに1つのsubagentへ割り当てる。各呼び出しのツール仕様に従い、戻り値のagent IDとIssue番号を対応づける。再開・修正依頼は同じ担当へ送り、担当が失われた場合は先に既存の変更・commit・PRを確認してから引き継ぐ。
- subagentはファイルシステムを共有するので、すべての編集・インストール・検証・Git操作を割り当てた絶対パス内で行うよう伝える。共有作業ディレクトリでのcheckoutや他担当のworktree編集をさせない。

委任時は次の情報を具体値で渡す。

```text
担当: <owner/repo>#<番号> とIssue URL
受け入れ条件: <本文・コメントから確認した条件>
作業場所: <worktreeの絶対パス>
ブランチ / 起点commit / PR base: <専用branch> / <SHA> / main
優先して確認するファイル・テスト: <関連する範囲>
依存関係・競合制約: <先行Issue、共有箇所、触れてはいけない他担当領域>

worktreeのAGENTS.mdと関連docsを確認し、担当Issueだけを調査・実装する。
必要なテストとdocsを更新し、リポジトリで定めた検証を行う。
新しい依存・競合や要件の不明点は親へ知らせる。対象を広げず、再委任しない。
担当worktree以外を変更しない。mainを変更・push・マージしない。
検証後に担当ブランチへcommit・pushし、main向けの個別PRを作成する。
PR本文は日本語で、問題と変更内容、検証結果、制約、Closes #<担当番号>を記載する。
既存PRがある場合は重複作成しない。自己マージせずworktreeを保持する。
結果としてIssue番号、状態、branch、worktree、commit SHA、変更概要、
検証コマンドと成否、PR URL、未解決事項と再開条件を返す。
```

## 進捗と結果確認

- 親はsubagentのメッセージと完了通知を受け取り、Issueごとに待機・実行中・PR作成済み・失敗/ブロックを追跡する。途中の状況報告だけを完了としない。
- テスト失敗や権限エラーは当該Issueに記録する。無関係な担当は続行する。リトライ前にremoteのbranchとPRの実在を確認し、応答不明のpushやPR作成を盲目的に繰り返さない。検証失敗を成功扱いにせず、原因を解消できないときは未完了として報告する。
- 完了報告を受けたら親がPRのbase/head、差分の範囲、Issueの受け入れ条件、検証結果を確認する。CIがある場合はその状態も確認し、ローカル検証と区別する。不備は同じ担当へ戻す。
- 全対象についてIssue・結果・検証・PR URL・残課題を表で集約する。待機や失敗も省略しない。マージまたは破棄の確認までworktreeを保持し、ユーザーの明示的な指示がない限りPRを自己マージしない。
