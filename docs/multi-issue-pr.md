# 複数Issueの個別PR作成

共有Skillは [multi-issue-pr](../.agents/skills/multi-issue-pr/SKILL.md) に配置する。Codexがリポジトリから読み込む `.agents/skills` 形式で、個人の設定変更やインストールスクリプトは不要。配置と呼び出しの仕様は [OpenAI公式ドキュメント](https://developers.openai.com/ja-JP/docs/build-skills) を参照。

リポジトリ内で、対象の番号を明示して依頼する。

```text
$multi-issue-pr #12 #18 #24
```

Issueの例にある `/multi-issue-pr #12 #18 #24` も依頼文として扱うが、専用のスラッシュコマンドを登録するものではない。Skillが見つからない環境ではファイルを直接指定して読み込ませる。GitHubへの読み書き、Git、およびsubagentの起動が可能な環境が必要。

対象は指定番号のみ。親が依存関係と変更箇所の競合を確認し、独立したIssueをそれぞれ専用のsubagent・branch・worktreeへ割り当てる。各担当は調査、実装、テスト、ドキュメント更新、commit・push、main向けPRの作成まで行う。先行変更が必要なIssueはそのPRがmainにマージされるまで待機し、無関係なIssueは続行する。自動マージはしない。

最終報告では指定した全Issueの状態、検証結果、PR URL、残課題を確認できる。失敗時は作業場所を保持し、再依頼時は既存のbranchとPRを確認して継続する。

## Skillの検証

指示文の文字列一致だけでは動作を確認できないため、Skillの変更時は次の架空シナリオを使って実行計画と最終報告を確認する。GitHubの変更、実PRの作成、実装担当の起動は行わない。Skillと入力だけを評価者へ渡し、観察結果を下表と照合する。

| 入力・状況 | 確認する動作 |
| --- | --- |
| `#101 #102 #101`。101はFAQ、102は独立した画像変更 | 対象は101と102の2件、別担当・branch・worktree・PRに分離し、同時実行数の範囲内で並列化 |
| 番号指定なし | 番号を質問し、未対応Issueを自動選定しない |
| 103は104の新APIに依存。104は未マージ。105は独立 | 104と105を進め、103はマージ待ち。104のPR作成のみでは103を開始しない |
| 106と107が同じ関数を大幅変更 | 競合を説明して順序を決定し、先行PRのmainへのマージ後に変更箇所を再評価して後続を開始 |
| 指定108が指定外109に依存 | 109を実装対象に加えず108を待機にする |
| 110と111が循環依存、112は独立。同時実行枠は1 | 110・111を待機にし、112を1担当へ割り当てる |
| 113に既存PR、114は閉じたIssue、115は取得不能 | 重複PRを作らず、再対応指示のない114をスキップし、115を未完了として報告 |
| 116の検証失敗、117成功、118はPR作成の応答不明 | 116を成功扱いせず、117のPRを報告、118は実在を確認してから再試行 |
| subagentツールが利用不可 | 並列実行を装わず、環境の制約を報告 |

Frontmatter・命名・未完の雛形は、`skill-creator` が提供する `scripts/quick_validate.py` にSkillディレクトリを渡して検証する。サイト全体の回帰検証は既存の `npm test` を使う。このシナリオ検証は実際の複数IssueからPRを作成する結合テストの代わりにはならない。
